# 챕터 4. 실행 흐름 — 요청부터 응답까지

**대상:** 비전공 초보  
**이 챕터 목표:** “요청이 들어오면 스프링이 어떤 순서로 처리하는지” 말로 설명할 수 있게 하기

---

## 1. 개념 설명

### 1-1. 비유: 회사 안내 데스크

1. **손님(클라이언트)** 이 “3층 회의실”을 찾음  
2. **1층 안내(톰캣/서블릿 컨테이너)** 가 요청을 받음  
3. **배달원(DispatcherServlet)** 이 “어느 부서(컨트롤러)가 맞는지” 확인  
4. **해당 부서(컨트롤러 메서드)** 가 일 처리  
5. **포장(JSON 변환 등)** 을 거쳐 손님에게 전달  

**왜 스프링이 이렇게 복잡해 보이나?**  
→ 개발자는 **컨트롤러만** 작성하면 되고, **나머지는 프레임워크가** 일정한 **규칙**으로 처리합니다.

---

## 2. 구조 (클래스가 아닌 “역할” 관점)

```
[ 클라이언트 ]
      │  HTTP (GET/POST, URL, Header, Body)
      ▼
[ 내장 톰캣 ]  ← 포트(8080) listen
      │
      ▼
[ DispatcherServlet ]  ← “Spring MVC의 앞단”
      │  매핑 검색: 어떤 @Controller 메서드?
      ▼
[ 컨트롤러 메서드 ]  ← @GetMapping 등
      │  반환: String / Map / DTO ...
      ▼
[ HttpMessageConverter ]  ← 객체 → JSON (Jackson 등)
      ▼
[ 응답 ]  Status + Header + Body
```

---

## 3. 코드 예제 (한 줄 요청 추적)

```java
@GetMapping("/api/users/{id}")
public UserResponse getUser(@PathVariable Long id) {
    return new UserResponse(id, "test");
}
```

**클라이언트:** `GET http://localhost:8080/api/users/7`

**처리 순서 (단계별):**

| 단계 | 무슨 일이 일어나나 |
|------|---------------------|
| 1 | 톰캣이 **소켓**에서 요청을 읽고 **HTTP 요청 객체**로 만든다 |
| 2 | **DispatcherServlet**이 “`/api/users/{id}` + GET”에 맞는 메서드를 찾는다 |
| 3 | URL에서 `7`을 **Long**으로 변환해 `id` 파라미터에 넣는다 (**PathVariable 매핑**) |
| 4 | `getUser(7)` 실행 → `UserResponse` 인스턴스 반환 |
| 5 | **Jackson**이 `UserResponse`를 JSON으로 바꾼다 **(HTTP 응답 본문)** |
| 6 | **200 OK** 와 함께 클라이언트로 전송 |

## 4. 실행 흐름 (POST로 조금 더)

**요청:**

```http
POST /api/users HTTP/1.1
Content-Type: application/json

{"name":"Kim","age":25}
```

**코드:**

```java
@PostMapping("/api/users")
public String create(@RequestBody UserCreateRequest body) {
    return "ok";
}
```

| 단계 | 설명 |
|------|------|
| **Content-Type** | `application/json` 이면 본문을 JSON으로 파싱한다 |
| **@RequestBody** | JSON → `UserCreateRequest` 객체 (필드명이 같아야 함) |
| **반환** | 문자열 `ok` → 응답 본문이 텍스트 `ok` |

**왜 JSON 필드명과 자바 필드명이 맞아야 하나?**  
→ 매핑이 **이름 기준**으로 이루어지기 때문입니다. (카멜케이스 통일 권장)

## 5. IntelliJ에서 흐름을 “보는” 방법

1. **디버깅:** 컨트롤러 메서드 첫 줄에 **중단점(Breakpoint)** → Run **Debug**  
2. **요청 한 번:** Postman 또는 브라우저(GET)  
3. **한 줄씩(F8)** 실행하면서 `id`, `body` 값 확인  

**왜 디버깅?**  
→ “어디까지 왔는지” 눈으로 확인하면 **흐름 이해**가 가장 빠릅니다.

## 6. 실무 팁 (흐름과 관련)

- **404:** 매핑에 없는 URL → 컨트롤러까지 안 옴  
- **415 Unsupported Media Type:** JSON이 아닌데 `@RequestBody`로 JSON 기대  
- **400 Bad Request:** JSON 형식 오류·타입 불일치 등  

로그에 `DispatcherServlet` 관련 로그 레벨을 올리면 **더 자세**히 볼 수 있으나, 입문 단계에서는 **컨트롤러 로그**만 찍어도 충분합니다.

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@RestController
public class UserController {
    private static final Logger log = LoggerFactory.getLogger(UserController.class);

    @GetMapping("/api/users/{id}")
    public UserResponse getUser(@PathVariable Long id) {
        log.info("getUser id={}", id);
        return new UserResponse(id, "test");
    }
}
```

## 7. 이 챕터 정리

- **톰캣**이 **HTTP**를 받고 → **DispatcherServlet**이 **어떤 메서드**인지 찾고 → **컨트롤러** 실행 → **반환값**을 JSON 등으로 변환  
- **애너테이션**은 “이 값을 URL/본문에서 어떻게 채울지”를 정해 줌
