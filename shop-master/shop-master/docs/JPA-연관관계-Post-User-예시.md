# JPA 연관관계 매핑: Post(게시글) ↔ User(작성자) 예시

`Post`와 `User`를 예로 들어, **연관관계를 매핑했을 때**와 **하지 않았을 때**를 비교합니다.

---

## 1. 연관관계 매핑을 했을 때 (자동)

JPA가 객체 간 연결을 알고 있으면, 개발자는 **객체 그래프를 점(`.`)으로 탐색**하면 됩니다.

```java
// 1. 게시글 하나를 조회한다.
Post post = postRepository.findById(1L).get();

// 2. 작성자 정보가 필요하면 그대로 꺼낸다. (별도 조회 로직을 매번 짤 필요 없음)
String userName = post.getUser().getName();
```

**특징**

- `post.getUser()`를 호출하는 시점에, 설정에 따라 JPA가 **Join이 포함된 쿼리**를 쓰거나 **추가 Select(Lazy)** 등으로 작성자를 로딩할 수 있습니다.
- 개발자는 **연결만 신뢰하고 객체를 따라가면** 됩니다.

---

## 2. 연관관계 매핑을 하지 않았을 때 (수동)

`Post`에 `Long userId`만 두고 User 엔티티와 연결하지 않은 경우입니다.

```java
// 1. 게시글을 조회한다.
Post post = postRepository.findById(1L).get();

// 2. 게시글에 저장된 userId를 꺼낸다.
Long userId = post.getUserId();

// 3. (직접 작성) 그 id로 유저를 다시 조회한다.
User user = userRepository.findById(userId).get();

// 4. 이제 이름을 얻을 수 있다.
String userName = user.getName();
```

**문제점**

- 연관 데이터를 쓸 때마다 **id → repository 조회** 패턴을 반복해야 합니다.
- 게시글 10개의 작성자 이름을 보려면, 루프마다 유저를 조회하는 식으로 **N+1에 가까운 비효율**이 생기기 쉽고, 이를 줄이려면 **배치 조회·캐시·수동 Join** 등을 또 직접 설계해야 합니다.

---

## 3. 연관관계를 맺으면 얻는 장점 (추가 정리)

| 구분 | 설명 |
|------|------|
| **표현력** | 도메인이 “게시글은 작성자를 갖는다”처럼 **객체 모델로** 드러나 읽기 쉽습니다. |
| **로딩 전략** | `FetchType.LAZY` / `EAGER`, `@EntityGraph`, `join fetch` 등으로 **언제·어떻게** 연관을 불러올지 JPA 수단으로 조절할 수 있습니다. |
| **N+1 대응** | Fetch Join, 배치 사이즈, DTO 프로젝션 등 **JPA·쿼리 최적화 패턴**을 같은 모델 위에서 적용하기 쉽습니다. |
| **Cascade·orphanRemoval** | 부모-자식 생명주기를 설정으로 맞출 수 있어, **삭제·저장 흐름**을 일관되게 가져가기 좋습니다. |
| **유지보수** | 작성자 접근이 `post.getUser()` 한 곳으로 모이면, 나중에 **로딩 방식이 바뀌어도** 호출부를 덜 고쳐도 됩니다. |

---

## 4. 한 줄 요약

- **매핑 O**: `post.getUser().getName()`처럼 **객체 그래프**로 의도를 표현하고, 로딩은 JPA/설정이 담당합니다.  
- **매핑 X**: `userId` + **직접 repository 조회**를 반복하며, 목록·성능 이슈는 **수동으로** 계속 맞춰야 합니다.
